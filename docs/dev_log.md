3.  **HWPX 타입 정의**: `src/shared/types.ts` 파일에 OWPML 표준 스키마를 기반으로 HWPX 문서 구조를 위한 TypeScript 인터페이스들을 정의했습니다.
4.  **스타일 맵핑 로직 추가**: `normalizeDocument` 함수에 `header.xml`에서 폰트, 테두리, 글자 모양, 단락 모양 등 다양한 스타일 정보를 추출하여 ID 기반으로 맵핑하는 로직을 추가했습니다.
5.  **본문 내용 정규화 초기 구현**: `sectionN.xml`에서 단락(`hp:p`), 텍스트 런(`hp:run`), 테이블(`hp:tbl`), 컨트롤(`hp:ctrl`)을 추출하여 `NormalizedDocument` 구조로 변환하는 초기 로직을 구현했습니다.

### 결정 사항
-   `normalizeDocument` 함수 내에서 스타일 정보는 ID를 키로 하는 Map 형태로 관리하여 빠른 참조가 가능하도록 했습니다.
-   본문 내용은 단락을 기준으로 정규화하며, 각 단락 내의 텍스트 런, 테이블, 컨트롤 등은 별도의 타입으로 정의하여 관리합니다.

### 다음 단계

## [2026-06-06] 파싱 안정성 강화 및 .hwp 지원 시작

### 완료된 작업
1.  **HWPX 파서 안정화**: XML 네임스페이스(`hp:`, `hh:`, `hs:`)가 없거나 다른 경우에도 유연하게 데이터를 찾을 수 있도록 `getVal` 헬퍼 함수를 도입하고 방어적 로직을 추가했습니다.
2.  **구조 유연화**: `headerData`나 `sectionsData` 내의 특정 필드가 누락되어도 앱이 크래시되지 않도록 Null Check를 강화했습니다.
3.  **.hwp 파일 인식**: 파일 열기 대화상자와 드래그 앤 드롭 UI에서 `.hwp` 확장자를 인식하고 처리할 수 있도록 업데이트했습니다.
4.  **바이너리 파서 구조 마련**: `src/core/parser/hwp_parser.ts`를 생성하여 `.hwp` 바이너리 파싱을 위한 아키텍처를 설계했습니다.

### 결정 사항
-   HWPX는 공식 표준(OWPML)을 따르지만, 실제 생성된 파일들은 네임스페이스 사용이 제각각일 수 있으므로 유연한 키 매칭 방식을 채택했습니다.
-   `.hwp` 지원은 우선 UI와 IPC 수준에서 경로를 확보하고, 실제 바이너리 파싱 엔진은 단계적으로 구현하기로 했습니다.

### 다음 단계

## [2026-06-06] 렌더링 최적화 및 HWP 바이너리 파서 연동 시작

### 완료된 작업
1.  **점진적 렌더링(Incremental Rendering) 도입**: 대용량 HWPX 파일 로딩 시 브라우저가 멈추는 현상을 방지하기 위해, 초기 50개 단락만 먼저 그리고 스크롤 시 추가로 로드하는 방식을 적용했습니다.
2.  **파싱 안전장치 추가**: `normalization.ts`에서 단락 파싱 개수를 최대 10,000개로 제한하고 섹션별 로깅을 강화하여 무한 루프 가능성을 차단했습니다.
3.  **HWP 바이너리 라이브러리 연동**: `cfb` 라이브러리를 설치하고 `hwp_parser.ts`에 연동하여 `.hwp` 파일의 내부 스트림(CFBF)을 추출할 수 있는 기초 로직을 구현했습니다.
4.  **UI/UX 개선**: 로딩 중 상태 표시와 대용량 문서 처리를 위한 무한 스크롤 기초 로직을 `App.tsx`에 반영했습니다.

### 결정 사항
-   성능 향상을 위해 `useMemo`를 사용하여 불필요한 리렌더링을 방지했습니다.
-   `.hwp` 지원을 위해 `cfb` 라이브러리를 사용하여 Compound File 구조를 분석하기 시작했습니다.

### 다음 단계
-   `.hwp` 파일의 `BodyText` 스트림에서 zlib 압축을 해제하고 실제 텍스트 레코드를 추출합니다.
-   표(Table) 내의 텍스트 렌더링 버그를 수정하고 스타일 반영을 고도화합니다.

## [2026-06-06] 단락 삭제 및 백스페이스 동작 안정화

3.  **데이터 유실 방지**: 모든 단락이 삭제되지 않도록 최소 한 개의 단락은 항상 유지하는 방어 로직을 스토어에 적용했습니다.
4.  **고유 ID 기반 렌더링**: 단락마다 고유한 ID를 생성하고 이를 React의 `key` 값으로 사용하여, 단락 삭제 시 다른 단락들이 예기치 않게 사라지거나 리렌더링되는 문제를 해결했습니다.

### 결정 사항
-   브라우저의 기본 삭제 동작이 React 상태와 충돌하지 않도록 `e.preventDefault()`를 적절히 사용하고 수동으로 상태를 관리합니다.

### 다음 단계
-   글자 서식(굵게, 크기 등) 변경 시에도 단락 구조가 깨지지 않도록 정밀한 렌더링 로직을 구축합니다.
-   문서 자동 저장 기능을 추가합니다.
